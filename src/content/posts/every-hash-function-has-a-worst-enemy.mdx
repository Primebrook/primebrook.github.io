**Hash functions** are fundamental in computer science. They're used in foundational data structures like sets, hash tables and bloom filters; they're also used in cryptography to conceal private information. So, what are hash functions? Well... they're functions that map an arbitrarily large input space to a **fixed size output space**. That's it.

<FiniteOutput label="Fig 1." caption="h maps an unbounded input space onto an output space of 8 values." />

Typically, the finite output space indexes an array in memory. For example, if the output space of a hash function is the integers between $0$ and $7$, then we're dealing with an array of size $8$. More explicitly, hashing relies on two core properties:

1. **Output space must have fixed size** - as mentioned above, this is the key property.
2. **Determinism** - a given input must map to the same output, every time.

with an optional third property in the case of cryptographic hash functions:

3. **Irreversibility** - Unable to go backwards from output to input (easily).

We won't worry about irreversibility in this post.

## Sets: How do they work?

The simplest hash based data structure is a **set**. A set is used for storing an unordered collection of distinct items (or "keys"). The most common operations to perform on a set are INSERTs and LOOKUPs ("is $y$ a member of my set?").

The process of inserting a key into a set is:

1. Encode the key to a positive integer (e.g. UTF-8), $x$
2. Compute the hash of the integer, $h(x)$
3. The computed hash value provides the memory address to store the key.

The process of looking up a specific key is:

1. Encode the key to a positive integer, $x$
2. Compute the hash of the integer, $h(x)$, to get the memory address
3. Check if memory address contains any values

These two operations are the core of all hash based data structures. For instance, hash tables (dictionaries in python) work the same way except they store a value alongside each key.

### Collisions & linked Lists

Since hash functions map a large space to a smaller space, you'd be correct in thinking that there often exist multiple inputs that get mapped to the same output value. When this happens in a set it's called a **collision** - and it complicates the lookup process.

We can't store multiple items at a single memory address - that defeats the purpose of having an "address". So, what to do? Well... we can store the first item at the address, $h(x)$, and keep with it a pointer to the location of the next element. At this second address we can keep the second item _and_ also a pointer to the third element... and so on. Does this sound familiar? This is just a linked list which starts at address $h(x)$. Fig 3 shows two examples of a set using different hash functions, the first example only has one collision which results in a linked list of length two, starting at memory address $1$; the second example shows a set with a high number of collisions resulting in two long linked lists.

**Long linked lists in a set are problematic** because they slow INSERTs and LOOKUPs down significantly. Performing an INSERT **without a collision** is an $O(1)$ operation. But if the INSERT maps to a location with $n$ items already living there, then it will take $n$ steps to traverse the list before appending the latest item to the end. This makes INSERTs **with a collision** an $O(n)$ operation - similarly, LOOKUPs on a linked list are $O(n)$ 😬.

Therefore a **good hash function** is one that spreads the keys out across buckets where the chance of collision is low. This ensures very few linked lists exist and when they do they're short in length so that, on average, set operations remain $O(1)$.

<details class="aside">
<summary>When collisions became an attack: HashDoS, 2011</summary>

At the 28th Chaos Communication Congress (28C3) in December 2011, Alexander Klink and Julian Wälde showed that the web platforms most of the internet ran on could be tied up by a single HTTP request. The talk is [Effective Denial of Service attacks against web application platforms](https://youtu.be/R2Cq3CLI6H8).

The attack is the slow lookup above, made deliberate. Web frameworks load a request's parameters into a hash table before the code ever runs. Their hash functions were fixed and public, so an attacker could work out offline thousands of parameter names that all land in the same bucket, and send them in one POST request. Each insert then scans the whole chain built so far: $n$ keys cost about $n^2/2$ comparisons instead of about $n$. One request could keep a server's CPU busy for minutes, and a handful of them could take it down.

PHP, ASP.NET, Java, Python and Ruby were all affected. The weakness had been described in 2003 by Crosby and Wallach, and Perl fixed it then; most other languages hadn't. The fix that stuck was to stop using a fixed hash function: Python, for example, has picked a random hash seed for strings every time it starts since version 3.3.

</details>

### Random inputs or random functions?

One way of getting good hashing is by assuming the inputs are random. We can assume the keys are nicely spread out, drawn from some uniform distribution, which means we won't get many collisions. But in the real world, data is clumpy, full of patterns (even adversarial) - so if we want our implementation to be useful, we cannot make any assumptions about our inputs.

Instead of assuming *random inputs*, perhaps we can make our choice of $h$ random? This is the idea behind **Universal Hashing**, it relocates the **randomness** from an area we don't control (inputs) to an area we do (choice of $h$). Universal hashing says that if we put together an appropriate **family of hash functions** then we can pick $h$ at random from this family and have mathematical guarantees about the collision rate, regardless of the input distribution (i.e. for any input, hence "universal"). This element of randomness when selecting $h$ protects us against potential adversaries who might otherwise deliberately pass in colliding keys to slow down look ups. Let's define what it means to be a universal family of hash functions below.

## Universal Family, $\mathcal{H}$

Let $U$ be a set of keys that we want to hash into an array of $m$ buckets. Let $\mathcal{H}$ be a _family of hash functions_. $\mathcal{H}$ is called a **universal family** if for every pair of different keys $x$ and $y$, the probability that they collide when $h$ is selected at random from $\mathcal{H}$ is at most $1/m$.

That's a bit wordy, let's take a moment to understand what's being said and why it's a strong claim.

**We**:

1. Pick ANY two different keys
2. Draw $h$ from $\mathcal{H}$ at random

**Guarantee we get back**:
1. Those two keys land in the same bucket with probability *at most $1/m$*

...this is no worse than if each key's bucket were picked by rolling an $m$-sided die. We've managed to capture randomness (and the nice uniformly spreading property it gives us) in our otherwise _deterministic_ hash function; recall determinism is a crucial requirement of hash functions (we need to be able to find a key after we have hashed it 🤓).
