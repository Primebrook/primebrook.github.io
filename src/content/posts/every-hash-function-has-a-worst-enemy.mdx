**Hash functions** are fundamental in computer science. They're used in foundational data structures like sets, hash tables (aka dictionaries) and bloom filters; they're also used in cryptography to conceal private information. So, what are hash functions? Well... they're functions that map an arbitrarily large input space to a **fixed size output space**. That's it.

<FiniteOutput label="Fig 1." caption="A function maps an unbounded input space onto an output space of fixed size." />

Often the finite output space that gets mapped to indexes an array in memory. To be more explicit, hashing relies on two core properties:

1. **Deterministic** - a given input must map to the same output, every time.
2. **Output space must have fixed size** - as mentioned above, this is the key property.

with an optional third property in the case of cryptographic hash functions:

3. **Irreversibility** - Unable to go backwards from output to input (easily).

We won't worry about irreversibility in this post.

### Hash Collisions

Since hash functions map a large space down to a smaller space, you'd be correct in thinking that some input values get mapped to the *same* output value, when this happens it's called a **collision** - and it's unideal. Let's explore why in the case of hash tables.

<HashMapping label="Fig 2." caption={"Keys mapped to indexes of an array by h(x)\u00a0=\u00a0x\u00a0mod\u00a08."} />

#### Collisions slow lookups down

Looking up data for a key in a set means computing $h$ for that key. The hash function used in Fig 2 above, $h(x) = x \bmod 8$, happens to map the keys 25 and 41 to the same bucket (bucket 1) - we call this double mapping a **collision**. And it's a bad thing. Why? Looking up data for a key in a hash table means computing $h(key)$, if there are no collisions then the answer you're looking for is in the only thing present in the bucket, simples. But if the bucket houses many keys (i.e. lots of collisions occurred), then you have to sift through each element in the bucket to check for your key, this takes linear time.

<details class="aside">
<summary>When collisions became an attack: HashDoS, 2011</summary>

At the 28th Chaos Communication Congress (28C3) in December 2011, Alexander Klink and Julian Wälde showed that the web platforms most of the internet ran on could be tied up by a single HTTP request. The talk is [Effective Denial of Service attacks against web application platforms](https://youtu.be/R2Cq3CLI6H8).

The attack is the slow lookup above, made deliberate. Web frameworks load a request's parameters into a hash table before your code ever runs. Their hash functions were fixed and public, so an attacker could work out offline thousands of parameter names that all land in the same bucket, and send them in one POST request. Each insert then scans the whole chain built so far: $n$ keys cost about $n^2/2$ comparisons instead of about $n$. One request could keep a server's CPU busy for minutes, and a handful of them could take it down.

PHP, ASP.NET, Java, Python and Ruby were all affected. The weakness had been described in 2003 by Crosby and Wallach, and Perl fixed it then; most other languages hadn't. The fix that stuck was to stop using a fixed hash function: Python, for example, has picked a random hash seed for strings every time it starts since version 3.3.

</details>
